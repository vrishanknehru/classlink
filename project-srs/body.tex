\hypertarget{introduction}{%
\section{Introduction}\label{introduction}}

\hypertarget{purpose}{%
\subsection{Purpose}\label{purpose}}

Taking attendance by roll call eats lecture time, and a signed sheet or a shouted "present" is easy to fake and hard to check later. ClassLink is the fix. It is a classroom attendance system where the teacher\textquotesingle s phone broadcasts a short lived Bluetooth Low Energy (BLE) token, each student\textquotesingle s phone hears it and sends a signed claim, and a server decides who counts as present. The main idea is that the phone never decides for itself, so the record can be trusted.

This document is the Software Requirements Specification (SRS) of ClassLink Version 1.0. It follows the approved project proposal (UCS503P). Requirements carry an ID such as FR (functional) and a priority from the MoSCoW scheme: Must (needed for the pilot), Should (next iteration), Could (optional). A Status column says what is built today.

\hypertarget{intended-audience-and-reading-suggestions}{%
\subsection{Intended Audience and Reading Suggestions}\label{intended-audience-and-reading-suggestions}}

This SRS is for developers, testers, pilot teachers, and the course instructor. It gives the internal, external, functional, and nonfunctional details of ClassLink. Every requirement is written so a test can check it.

Key terms used in this document:

\begin{itemize}
\tightlist
\item
  \textbf{BLE (Bluetooth Low Energy)}: the short range radio the phones use. It needs no pairing.
\item
  \textbf{Token}: a 17 byte code the teacher phone broadcasts. It changes every 15 seconds and names no person.
\item
  \textbf{Challenge (nonce)}: a one time code the server gives a student before a check in, so nobody can reuse an old claim.
\item
  \textbf{Claim}: the signed message a student phone sends. It holds the one time code, token, signal strength, sample count, and time.
\item
  \textbf{RSSI}: received signal strength in dBm. A larger number (closer to zero) means a closer phone.
\item
  \textbf{Session}: one class period in which attendance is open.
\item
  \textbf{Device key}: the signing key kept on a student\textquotesingle s phone. The server stores only its public half.
\item
  \textbf{Audit log}: the server\textquotesingle s permanent record of who did what.
\item
  \textbf{POC}: the earlier offline proof of concept app.
\end{itemize}

\hypertarget{project-scope}{%
\subsection{Project Scope}\label{project-scope}}

ClassLink gives Teachers and Students one place to run attendance, and gives the Administrator control over who may teach. It records presence only. It does not grade, schedule, or track location.

\textbf{Objectives.}

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\tightlist
\item
  Speed: a student checks in within 10 seconds of starting the scan, so roll call stops costing lecture time.
\item
  Trust: the server verifies every claim, so a phone cannot mark itself present.
\item
  Traceability: every claim, rejection, and correction leaves a record.
\item
  Teacher control: a live roster, manual corrections with a reason, and CSV export.
\item
  Privacy: the system keeps only name, roll number, email, a device public key, and attendance. It never collects location.
\item
  Engineering quality: the backend passes Ruff and strict MyPy, and every requirement marked Done has an automated test run in CI.
\end{enumerate}

\textbf{In scope.} Teacher and student roles on Android and iOS, built from one Flutter code base. Classrooms with join codes. One registered phone per student. Attendance sessions with a signal strength rule. A live roster, manual corrections, and CSV export. An audit log. Testing on real phones in a real room.

\textbf{Optional extensions} (outside this course submission). Links to learning management systems, and a signal threshold that adapts to each room.

\textbf{Out of scope.} Proving that the phone\textquotesingle s owner is the person holding it. Student to student relaying. Grading and timetables.

\textbf{Status terms.} \emph{Done} means built and covered by an automated test. \emph{POC} means present only in the offline proof of concept. \emph{Planned} means specified but not built. Today the server side is built and tested. The mobile apps (Android and iOS) do not call it yet, so anything that needs an app is Planned.

\hypertarget{product-perspective}{%
\subsection{Product Perspective}\label{product-perspective}}

ClassLink grew from an offline proof of concept, the Flutter app in \texttt{code/}, that showed a teacher phone can announce a session over BLE and a student phone can check in by proximity. Version 1.0 adds a server so the result no longer depends on trusting the student\textquotesingle s phone. It follows a layered client and server design (Figure 2.1).

\begin{itemize}
\tightlist
\item
  \textbf{Mobile app:} Flutter, for Android and iOS, with a teacher mode and a student mode.
\item
  \textbf{Backend API:} FastAPI (Python) for sign in checks, validation, sessions, and claims.
\item
  \textbf{Business logic:} rotating tokens, claim checks, corrections, and export.
\item
  \textbf{Database:} Supabase Postgres. Supabase Auth signs users in.
\end{itemize}

\begin{figure}
\centering
\includegraphics[width=0.8\textwidth,height=\textheight,keepaspectratio]{figures/fig_arch.pdf}
\caption{High-level system architecture.}
\end{figure}

One check in works like this. The teacher app fetches a fresh token from the server every 15 seconds and broadcasts it. A student phone hears the token and asks the server for a one time challenge. The phone measures signal strength for a few seconds, signs the result with its own key, and sends it. The server verifies the claim and records attendance.

\hypertarget{user-classes-and-characteristics}{%
\subsection{User Classes and Characteristics}\label{user-classes-and-characteristics}}

ClassLink has four user classes (Figure 2.2).

\begin{itemize}
\tightlist
\item
  \textbf{Teacher.} Runs sessions for classrooms they own. The role comes only from a list of approved teacher emails kept by the administrator.
\item
  \textbf{Student.} Joins classrooms with a join code and checks in with one registered phone.
\item
  \textbf{Administrator.} Sets up the server and edits the approved teacher list. This is not an in app role.
\item
  \textbf{Evaluator.} Reads the exported CSV files. No app access needed.
\end{itemize}

Supabase Auth is the one external system. It signs users in and issues their tokens.

Students and teachers need only basic phone skills. The administrator needs medium technical skill.

\hypertarget{product-functions}{%
\subsection{Product Functions}\label{product-functions}}

ClassLink stores classrooms, sessions, and attendance, and keeps a record of every important action. At a high level it lets users sign in and get a role, create or join a classroom, register a device key, start and end sessions with rotating tokens, check in with a signed claim, watch a live roster, correct mistakes with a reason, and export a CSV. Users must sign in before using any of these functions.

The main data records are:

\begin{itemize}
\tightlist
\item
  \textbf{profiles}: user id, role (teacher or student), full name, roll number, email.
\item
  \textbf{classrooms}: classroom id, teacher id, name, unique join code.
\item
  \textbf{enrollments}: classroom id and student id, with the join time.
\item
  \textbf{devices}: student id, public key, label, time it was cancelled. A student has one active device.
\item
  \textbf{sessions}: classroom id, alias, signal threshold, sample window, minimum samples, start and end time. A classroom has at most one active session.
\item
  \textbf{challenges}: session id, student id, token, issue and expiry time, used time. Each is single use.
\item
  \textbf{attendance}: session id, student id, status, source (BLE claim or manual correction), median RSSI, sample count, time of measurement, and correction details. One record per student per session.
\item
  \textbf{audit\_events}: actor, action, subject, details, time.
\end{itemize}

\hypertarget{operating-environment}{%
\subsection{Operating Environment}\label{operating-environment}}

Students and teachers use an Android phone (8.0 or later) or an iPhone, both with Bluetooth LE. The lowest iOS version is still to be confirmed. The teacher phone must support BLE advertising, so we test on real phones of both kinds. The server runs in a Linux container behind HTTPS. The database is Supabase Postgres. Phones need internet during check in, but the Bluetooth exchange itself does not.

\textbf{External interfaces.}

\begin{itemize}
\tightlist
\item
  \textbf{User interface:} a Flutter app with a teacher mode (classrooms, session control, live roster, corrections, export) and a student mode (join, register phone, check in, result). Every rejection shows a plain explanation.
\item
  \textbf{Hardware:} Bluetooth LE radio. The teacher phone needs BLE advertising. No other hardware.
\item
  \textbf{Software:} FastAPI backend, Supabase Postgres, Supabase Auth, GitHub Actions for CI.
\item
  \textbf{Communications:} HTTPS with JSON over REST. A Supabase sign in token (JWT) in the Authorization header. A 17 byte token inside the BLE advertisement.
\end{itemize}

\textbf{Design and implementation constraints.}

\begin{itemize}
\tightlist
\item
  Stack: Flutter (Android and iOS), FastAPI on Python 3.11 or later, psycopg 3, Supabase Postgres and Auth.
\item
  A phone never creates an attendance record on its own. Only the server decides.
\item
  Secrets stay on the server. Only \texttt{.env.example} files enter the repository.
\item
  The BLE token is 17 bytes and travels in the manufacturer data field of the BLE advertisement, because a service identifier plus the token does not fit in a basic one. We have not yet confirmed this layout on phones. iOS only lets an app advertise a local name and service identifiers, so an iPhone may not be able to broadcast the token this way. We test this first, and the token layout or the teacher device may need to change.
\item
  Apps write only through the API. The database gives apps read only access to their own rows.
\item
  Four person team, one semester, with the work split across backend, app, documentation, and testing.
\end{itemize}

\textbf{Assumptions and dependencies.}

\begin{itemize}
\tightlist
\item
  Students use the phone they registered. A student who changes phones registers again.
\item
  Phone and server clocks stay within about a minute.
\item
  Supabase free tier limits are enough for the pilot.
\item
  Signal strength is noisy, so the server uses the median of several samples against a per session threshold. The right threshold is tuned on real phones.
\end{itemize}

\textbf{UC-1 Check in to a session.} Actor: student, who must be signed in, enrolled, and have a registered phone. The teacher has a session running. The student taps Check in. The app scans for the token for the sample window and requests a challenge. The server checks the token, session, enrollment, and device, then issues a one time code. The app signs the claim and sends it. The server checks the one time code, signature, time, sample count, and median signal, then records attendance and shows Present. If the signal is weak or samples are too few, the student sees a plain message and may move closer and retry. Any other failure shows its reason code and nothing is recorded.

\textbf{UC-2 Correct attendance.} Actor: teacher, who owns the classroom. The teacher opens the roster, picks a student, and marks them present or absent with a reason of at least five characters. The server stores the change with the teacher\textquotesingle s name and writes an audit event. A reason that is too short is refused and nothing changes.

The design rules behind these flows:

\begin{itemize}
\tightlist
\item
  \textbf{Teacher broadcasts, student listens.} There is no relay between students.
\item
  \textbf{The server decides.} Every claim is checked on the server.
\item
  \textbf{Real data only.} Evaluation figures come only from recorded real runs.
\end{itemize}

\hypertarget{system-features}{%
\section{System Features}\label{system-features}}

ClassLink is a classroom attendance system. The main part of this product is to accept a signed BLE claim and decide on the server whether it counts.

\hypertarget{description-and-priority}{%
\subsection{Description and Priority}\label{description-and-priority}}

ClassLink has main features and some sub features. In priority order, from top to bottom:

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\tightlist
\item
  \textbf{Attendance claims} (Must, pilot): challenge, signed claim, server checks. This is the goal feature of the software.
\item
  \textbf{Sessions and tokens} (Must, pilot): start and end sessions, rotating BLE token.
\item
  \textbf{Device binding} (Must, pilot): one registered key per student.
\item
  \textbf{Accounts and classrooms} (Must, pilot): sign in, roles, join codes.
\item
  \textbf{Roster and corrections} (Must, pilot): live list, fixes with a reason.
\item
  \textbf{Export and audit} (Should): CSV download and audit log.
\item
  \textbf{Offline mode} (Could): the original no server demo, labelled as not the official record.
\end{enumerate}

The first meaningful milestone is a working pilot where a teacher starts a session, a student checks in from a real phone, and the roster shows the result. The server side of this is done. The app side is planned.

These are targets. We report only values measured in the pilot.

\begin{itemize}
\tightlist
\item
  Discovery: a student phone shall pick up the token within 5 seconds in the same room.
\item
  Check in: from scan start to server result within 10 seconds.

  API: p95 under 500 ms for challenge and claim calls with 50 students at once.
\item
  Capacity: one classroom of 300 students with up to 150 check ins at once.
\end{itemize}

\hypertarget{security-requirements}{%
\subsection{Security Requirements}\label{security-requirements}}

\begin{itemize}
\tightlist
\item
  All traffic shall use HTTPS in production.
\item
  Secrets, such as the token key and database credentials, shall exist only on the server. CI shall fail if a \texttt{.env} file or keystore is committed.
\item
  The database shall have row level security on every table, so each user sees only their own rows. Apps read but never write.
\item
  A signed claim shall cover the session, one time code, token, signal strength, sample count, and time, so changing any value breaks the signature.
\item
  The server shall compare token tags with a timing safe method, and check every request\textquotesingle s sign in token for its signature, expiry, and intended use.
\item
  The system shall store only name, roll number, email, a device public key, and attendance. It shall not collect location.
\end{itemize}

ClassLink stops casual proxy attendance (a friend marking you present). It does not stop a friend who holds the student\textquotesingle s unlocked phone, or someone who relays a live token to a faraway phone within its few seconds of life. Short token periods, the signal rule, and the audit log reduce these risks but do not remove them.

\hypertarget{software-quality-attributes}{%
\subsection{Software Quality Attributes}\label{software-quality-attributes}}

\begin{itemize}
\tightlist
\item
  \textbf{Reliability:} attendance writes happen fully or not at all, so a retry is safe. If two claims for one student arrive together, only one record is made.
\item
  \textbf{Availability:} the pages \texttt{/healthz} and \texttt{/readyz} report whether the server and database are working.
\item
  \textbf{Maintainability:} the backend passes Ruff and strict MyPy in CI, and every Done requirement has an automated test.
\item
  \textbf{Portability:} the server runs from one ready to run package (a container image) and is set up with environment variables.
\item
  \textbf{Usability:} a student checks in with one tap, and every rejection has a plain explanation.
\end{itemize}

\hypertarget{business-rules}{%
\subsection{Business Rules}\label{business-rules}}

\begin{itemize}
\tightlist
\item
  A student has at most one attendance record per session.
\item
  Only a classroom\textquotesingle s teacher can see or change its attendance.
\item
  A manual correction always has a reason and a named teacher.
\item
  An ended session never restarts. A new session gets new tokens.
\item
  A student has one active phone. Replacing it cancels the old key.
\item
  Only the administrator decides who becomes a teacher.
\end{itemize}

\hypertarget{other-requirements}{%
\section{Other Requirements}\label{other-requirements}}

ClassLink needs maintenance after the course, because phones, Android and iOS versions, and BLE behaviour keep changing. Other requirements are:

\begin{itemize}
\tightlist
\item
  \textbf{Documentation:} the repository holds this SRS in Markdown and LaTeX, the project proposal, UML diagrams, the deployment runbook, and the API reference served at \texttt{/docs}.
\item
  \textbf{Deployment:} the server is packaged as a container that does not run as an admin user, and it refuses to start in production without its database address and secrets. The administrator runs the database setup file on Supabase before the first start. GitHub Actions runs the app and server checks and rejects committed secrets. The team publishes a signed Android APK and an iOS build for the pilot. How the iOS build reaches testers is still to be decided. See \texttt{docs/deployment.md}.
\item
  \textbf{Privacy:} pilot participants learn what the app stores before they join a classroom. Deleting a user deletes their profile, enrollments, devices, and attendance. English only in the first version.
\item
  \textbf{Phasing:} Phase 1 (done): server, database schema, tests, CI, and documents. Phase 2 (planned): Android and iOS apps with sign in, key storage, token broadcast, scan and claim, and roster screens. Phase 3 (planned): pilot on real phones in a real room, with measured results. Extensions follow only after the pilot.
\item
  \textbf{Open issues to confirm:} whether the 17 byte token fits the BLE advertisement on real Android and iOS phones, and whether an iPhone can act as the teacher device; the signal threshold that works in a real room; whether to move the sign in token from a shared secret to public key signing; the Android application id, which still carries the old proof of concept name; and the consent wording for pilot students.
\end{itemize}
