\section{Introduction}\label{introduction}}

\hypertarget{purpose}{%
\subsection{Purpose}\label{purpose}}

This document specifies the requirements for ClassLink version 1.0, a classroom attendance system that replaces manual roll call with a Bluetooth Low Energy (BLE) proximity check and a server authoritative record. It defines what the system does, the constraints it works within, and how the team will judge that it works.

The specification covers the whole system: the Android application used by teachers and students, the backend service, and the database. It also records which requirements the repository satisfies today, so a reader never has to guess whether a feature exists.

\hypertarget{project-scope}{%
\subsection{Project Scope}\label{project-scope}}

Manual attendance is slow, easy to proxy, and hard to audit. ClassLink lets a teacher\textquotesingle s phone broadcast a short lived BLE token during a session. Enrolled students\textquotesingle{} phones detect the token, collect several signal strength samples, and send a signed attendance claim to a server. The server decides whether the claim counts.

\textbf{In scope for version 1.0}

\begin{itemize}
\tightlist
\item
  Teacher and student roles on Android, with sign in through Supabase Auth.
\item
  Classrooms, join codes, and enrollment.
\item
  One bound signing key per student device.
\item
  Attendance sessions with rotating BLE tokens and a per session proximity policy.
\item
  Server side validation of every claim, with a machine readable reason for every rejection.
\item
  A live teacher roster, manual corrections with a mandatory reason, and CSV export.
\item
  An audit trail for security relevant actions.
\item
  Evaluation on real devices in a real classroom.
\end{itemize}

\textbf{Out of scope for version 1.0}

\begin{itemize}
\tightlist
\item
  Proof that the human owner of a phone is present. ClassLink verifies that a bound, locally authenticated device observed a valid classroom beacon under the configured policy. It does not claim more.
\item
  Bluetooth mesh or any student to student relay.
\item
  Tested iOS support. Some iOS code paths exist in the proof of concept but no iOS device test evidence exists.
\item
  Integration with learning management systems, grading, or timetables.
\item
  Cross course attendance percentages and analytics dashboards.
\end{itemize}

\textbf{Goal.} Cut the time spent on attendance to seconds per student while producing an auditable record. The primary success measure is detection success rate on labelled positions in a real room (Appendix D).

Data flow for one check in:

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\tightlist
\item
  The teacher app asks the API for the current token (\texttt{GET\ /v1/sessions/\{id\}/token}) every 15 seconds and advertises it.
\item
  The student app scans, reads the token, and requests a challenge (\texttt{POST\ /v1/attendance/challenge}). The server checks the token, enrollment, and device binding, then returns a single use nonce and the session policy.
\item
  The student app samples RSSI for the session window, takes the median, signs a canonical claim string with the device key, and submits it (\texttt{POST\ /v1/attendance/claim}).
\item
  The server verifies the signature and policy, records attendance atomically, and returns the result. The teacher roster shows the new record.
\end{enumerate}

\hypertarget{operating-environment}{%
\subsection{Operating Environment}\label{operating-environment}}

\begin{itemize}
\tightlist
\item
  \textbf{Mobile.} Android 8.0 (API 26) or later with a Bluetooth LE radio. The teacher device must support BLE peripheral advertising, which depends on hardware and vendor firmware. This is why testing happens on physical devices only.
\item
  \textbf{Backend.} Linux container running Python 3.11 or later behind HTTPS.
\item
  \textbf{Database.} Supabase Postgres (PostgreSQL 15 or later) with the \texttt{auth} schema provided by Supabase.
\item
  \textbf{Network.} Phones need internet access during check in. The BLE exchange itself needs no network.
\item
  \textbf{Development.} Flutter stable (Dart 3.9 or later), Ruff, MyPy, Pytest, GitHub Actions.
\end{itemize}

\midrule\noalign{}
\endhead
\bottomrule\noalign{}
\endlastfoot
CON-01 & Android is the primary tested platform. Abstractions stay portable but the project makes no claim about untested platforms. \\
CON-02 & The BLE payload carries at most 20 bytes of application data and no student or teacher identifier. The token is 17 bytes. A legacy advertisement holds 31 bytes in total, and a 128 bit service UUID plus the token does not fit, so the token travels as manufacturer data only (3 bytes of flags, 2 bytes of company id, 2 bytes of length and type, 17 bytes of token, 24 in all) and students scan without a service filter. CON-03 & The teacher advertises and the student scans. There is no mesh and no student to student relay. \\
CON-04 & The server is authoritative. A client\textquotesingle s own decision never creates an attendance record. \\
CON-05 & The token HMAC secret, database credentials, and Supabase service keys exist only on the server. Only \texttt{.env.example} files enter the repository. \\
CON-06 & The stack is Flutter, FastAPI, and Supabase Postgres. \\
CON-07 & The system treats RSSI as noisy evidence, never as exact distance. It decides on the median of several samples, and the threshold and sample policy belong to each session. \\
CON-08 & Clients write data only through the API. Row level security gives clients read only access to their own rows. \\
CON-09 & Evaluation figures come only from recorded real runs. No figure appears in a report before the raw data exists in the repository. \\
\end{longtable}

\hypertarget{assumptions-and-dependencies}{%
\subsection{Assumptions and Dependencies}\label{assumptions-and-dependencies}}

\begin{itemize}
\tightlist
\item
  Students attend with the phone they bound. A student who changes phones rebinds, and the change is audited.
\item
  Supabase issues HS256 signed JWTs verified with the project JWT secret. Projects that use asymmetric signing keys need JWKS verification, which version 1.0 does not implement.
\item
  Server and phone clocks stay within about a minute of each other. The server uses its own clock for every freshness decision.
\end{itemize}

\hypertarget{deployment}{%
\subsection{Deployment}\label{deployment}}

\begin{itemize}
\tightlist
\item
  \textbf{OTHER-DEP-01.} The backend shall build into a container image with a non root user and run under Uvicorn.
\item
  \textbf{OTHER-DEP-02.} Configuration shall come from \texttt{CLASSLINK\_*} environment variables. The \texttt{.env.example} file in the backend folder documents every variable.
\item
  \textbf{OTHER-DEP-03.} The administrator shall apply \texttt{backend/migrations/0001\_init.sql} to the Supabase project before the first start.
\item
  \textbf{OTHER-DEP-04.} In production the service shall refuse to start without a database URL, a JWT secret, and a token HMAC secret of at least 16 characters.
\item
  \textbf{OTHER-DEP-05.} GitHub Actions shall run the Flutter analyzer and tests, the backend lint, type check and tests (with a Postgres service), and a check for committed secrets on every change.
\item
  \textbf{OTHER-DEP-06.} The project shall publish a signed Android APK for pilot installation.
\end{itemize}
